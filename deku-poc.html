The evaluator

We grade behaviour, not code. It cannot be fooled by source that looks correct but does not run - the only way to score is to actually work.

Why now

Every existing benchmark measures the easy half

  • Today's tools are scored on toy tasks

    Patch a repo, fix one function, pass one unit test. The hard part - designing the system and standing it up - is already done for them.

  • What customers actually buy is zero-to-one

    “Here is what I need - build me the app.” Nobody measures that, because you have to run the software to know whether it works.

  • So Deku is both a ruler and a factory

    It scores any model or agent, and the 80,000 recorded runs become training data that makes the next agent better.

Prior art we differentiate from - SWE-bench / Multi-SWE-bench (patch an existing repo) · WebArena / OSWorld (drive someone else's app) · HumanEval / LiveCodeBench (a single function). Deku is the case where the agent owns the whole stack.

Workstream 2 · Harness

How a trajectory is generated

Harbor owns the runner; Deku owns everything task-shaped. There is no bespoke CLI - every run goes through one command.

harbor run -p tasks/<task-id> \
           -a openhands \
           -m anthropic/claude-opus-4-8 \
           --n-concurrent 8
harbor run -p tasks/<task-id> -a oracle   # our reference app  -> must score exactly 1.0
harbor run -p tasks/<task-id> -a nop      # builds nothing     -> must score exactly 0.0

The nop run is a standing sanity check: if an agent that does nothing scores above zero, some workflow is passable without building anything.

StepWhat Harbor does
01Read and validate the task config - schema, resources, network mode, artefact rules
02Build the environment image from the task's Dockerfile
03Start the environment - the agent container runs as the main compose service, and the task's sidecars share its network namespace
04Wait for sidecar healthchecks - the database, auth server and inbox must be genuinely ready before the agent starts
05Inject environment variables - agent tier only. Admin and inbox-inspection credentials are withheld and given to the verifier instead
06Run the agent - the spec becomes its prompt, and it works until it finishes or hits the time cap
07Close the agent phase - this is why the app server must be started fully detached
08Collect artefacts - the agent's source is copied out, so it survives even if the verifier fails
09Run the verifier inside the still-running environment, where the app is still alive
10Read the reward - it becomes the trial score, written alongside the full trajectory
Two load-bearing boundaries

Step 5 is security. An agent holding the backend admin key could satisfy workflows by writing state directly instead of implementing the feature - the highest-value exploit in the harness. Step 7 is correctness. An app started as an ordinary background job dies with the session, and a complete, working application then scores zero because nothing is listening when grading begins.

Agent integrationWhy it matters
Browser tool must be enabledSelf-testing predicts success at r = 0.72. A profile without browser access makes that metric structurally zero and quietly changes what we measure.
No single call over 50K input tokensContext condensation over 100–200 turns can mangle the requirements - and the spec is the only document the agent gets.
Pin the OpenHands versionHarbor's adapter targets an entrypoint recent releases restructured away. Unpinned installs fail on the first call.
Strip conflicting sampling parametersOpenHands sends both temperature and top_p, which current Opus models reject outright - the agent dies at step 4. Fixed at the one choke point every agent passes through.

Pin the agent version alongside the runner version and both image digests. Calibration compares models against a fixed agent - a silent agent upgrade re-scopes every difficulty label in the corpus. For reference, the public VCB scaffold is stock OpenHands v0.59.0 with no source modification; their customisation was delivered entirely through a runtime system prompt.

Two hard stops - the oracle gate (our own reference implementation must score exactly 1.0, twice) and the anti-gaming audit (0% exploit rate).

Why the score is trustworthy

Two independent graders

Neither reads the source - a green “Payment successful” screen proves nothing on its own.

Runs first

Browser agent - can a person do this?

Sees only the rendered UI. Signs in, clicks, fills forms, reads the screen. A fresh session per journey.

Runs second

pytest - did it actually happen?

Queries the database, payment API, inbox and object store directly. Asserts permissions at the API, not in the UI.

How a score is built

A journey passes if ≥ 90% of its steps pass and every critical step passes.

score = journeys passed ÷ total journeys

Deploy failure is a hard zero. A design-quality reviewer also runs, but it is advisory and never moves the score - a “looks nice” number is trivially gamed.

Seven gates. Each one is a hard stop.

The order of the gates and the pass condition on each are fixed. Every cycle time is TBD - set from measurement during batch B0, not asserted in advance.

Why six and not three

A jump straight from 1,000 to 7,000 commits six sevenths of the corpus on one gate result. Splitting the back half means a defect found at 2,000 costs 1,000 tasks of rework instead of 6,000 - and each gate asks a different question, so a batch that passes throughput can still fail on coverage.

The compute arithmetic, sized on the worst case - 7,000 tasks × 8 trials, each held to the agent time cap, is 280,000 machine-hours. At 500-way that is ~23 days of wall clock; at 1,000-way, ~12. Trials that finish early return the balance, so this is a ceiling rather than a forecast - but the sweep still consumes a large share of the window, which is why concurrency is the B2 gate.

Status

Where we actually are

  • Built - the platform, end to end

    Realistic environments, the agent build loop, behaviour-based grading, the scoring engine and a full audit trail. The architecture runs.

  • Not yet proven end-to-end on an admitted task

    This is content-and-scale work, not architecture work - the normal phase after a platform is built.

  • Blocker 1 - reference solutions

    A task is admitted only once a known-good implementation scores a perfect run. Authoring those is underway.

  • Blocker 2 - grader throughput

    The browser grader competes for the same API limit as the agent that just ran. Dedicated capacity before large batches.

Next milestones in order - (1) pass the fairness gate on one task · (2) resolve grader rate-limiting · (3) admit a first batch and publish a head-to-head model comparison.
